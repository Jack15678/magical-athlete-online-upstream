## 文档明确规定的流程

- **第 1 页开头：** 第三场比赛开始前，先选定本场参赛角色，再翻开角色牌堆顶牌，按对应行增加本场规则。不是重新选秀，也没有写每三场再触发一次。
- 事件表共 **36 行**，恰好覆盖项目基础盒 36 个角色。没有 Second Wind、Extra Mile、LEAF 或 Wurstii 扩展角色的事件映射。
- 除注明赛前、回合开始或赛末的事件外，规则在本场持续生效。事件是一条公共附加规则，不是只赋予翻出的那张角色的控制者。
- **第 2 页 Imichateur / Copycat 红色边注：** 需要补牌时，把已弃置的牌洗混后再抽。边注紧随该事件，不能直接宣称它规定所有事件牌与复制牌的全局回收方式。
- **第 3 页 Sisyphe / Sisyphus 红色边注：** 未花掉的分数在赛后保留。
- **第 3 页 Tatillon / Stickler 正文：** 不追加规则。旁边“再抽一张？”是玩笑式边注，不是正文给出的强制重抽步骤。

## 完整事件表与角色 ID

下表“执行者”中的“当前角色”指正在完成该移动/回合的运动员；“玩家”保留原文 `joueur / personne` 的区分。2 人模式一人控制两个角色时，这种区分需要额外裁定，不能直接把玩家统一替换成角色。

“没有给出的裁定”是实现核对项，**不等于每项都阻塞**。原文没有覆盖的普通掷骰、移动、停下、同时效果、平局比较与能力完成顺序，应优先沿用项目已核验的基础规则。真正改变事件定义、无法只靠基础规则填补的缺口集中在：2 人发牌/受益目标、未选牌不足与扩展牌翻牌、末位颁奖/提前结束，以及分支地图兼容。单独的超时默认值、网络投影与任务排队属于网页实现决定。

## 不能从该 PDF 补出的通用裁定

1. **触发牌来源和生命周期。** “角色牌堆顶”明确不是所有角色均匀随机抽一个 ID，但文中没有独立事件牌堆；没有说明触发牌是放回、弃置还是暂时保留，也未讲扩展牌堆翻到无事件角色如何处理。当前实际抽牌器会排除玩家手牌、已用牌、场上角色及保留牌，这与另建 36 张独立牌堆是不同规则。
2. **2 人模式。** 原文同时使用“每个玩家”“你的运动员”“左边的人”，没有双角色专节。项目经典 2 人每场有 4 个运动员；每人只发 1 张会直接破坏出场数量。不能把这份缺口当成防御性边界，而应先定案再开放 2 人事件。
3. **6/8 场和多张地图。** 文中只规定第三场，也只用基础赛道 3、5、15 和 5/10/15/20/25 格及 Wild 背面。自选适用场次、分支赛道的标记前进路径和“左右”选择均是网页扩展，不是原文已有规则。
4. **NPC 与原有能力。** 文中要求放置另一个 Baba Yaga / M.O.U.T.H. / Blimp / Huge Baby / Party Animal / Legs / Egg 标记，但未定义其是否属于可选目标、有无玩家归属、能否被交换/淘汰、能否触发蹭蹭怪。将它们塞进普通 `racers` 会错误改变排名、同格人数、比赛结束和玩家投影。
5. **牌交换与棋子控制。** 3 个事件重发/传递/交换角色牌，另有每回合换牌与复用旧角色。原文没有区分“身体/身份/控制者/能力资源”；当前引擎已区分 `identityPlayerId` 与 `playerId`，不能随意选一种而称为原作者裁定。
6. **秘密选择与效果优先级。** 猜测必须先提交、再统一揭示；现有单个 `PendingChoice` 可串行收集，但不得在公共日志或其他玩家投影提前公开。原文没有给出超时、多人重掷竞价、与全部角色能力的裁定表。

## 接入时采用的方案（原提议，现已实现）

- 不改历史 `fan-v3` / `wurstii-v1` 引擎。先把明确支持的事件规则版本保存在 `MatchPlan` 和每场状态中，事件揭示结果也持久化，刷新/重试不能重抽。事件发生在选择全部提交之后、`beforeRace` 任务之前；这个时序来自第 1 页。
- 继续使用 JSON `Task` 队列和现有 `ask()` / `choose` 协议。集中一个事件模块，按赛前、回合开始、主骰、移动结束、回合结束、赛末接入，不另造通用规则 DSL 或第二个并行引擎。
- 如开放全部 36 个事件，只需针对会改变事件定义的缺口制定并注明网页裁定，普通时序沿用基础引擎；不必逐条求得作者答复才能开发。不能悄悄只实现简单事件、重抽困难事件，却仍把选项称为完整 Thrilling Thirds。
- `drawUnchosen()` 是当前唯一合法未选牌抽取入口。新增触发牌/额外能力牌保留区时，把它纳入同一物理牌区检查；Copycat 的弃牌回收可复用现有洗牌路径。不要另开复制牌池，导致同一实体牌同时在手牌、触发区和能力区。
- NPC 使用事件状态中的标记位置；不加到正常参赛者列表。这样现有角色数、排名、同格人数和 2 人固定顺序不会被标记误改。具体参与哪些技能仍须裁定。
- 所有事件得失分统一走现有积分入口并明确分类为 `scoreLedger.event`。当前 `points()` 只分 `map` 与 `skill`，不能让“事件得分”继续计入技能栏；逐场合计仍应等于真实积分增量。
- “倒数名次领奖”和“计时标记终止”需要在原有 `finish()` / `endRace()` 之间明确奖项和终止策略；当前第二名确定就结算，不能只换 UI 标签。
- 具体回归应覆盖：事件只抽一次并在恢复后保持；所有牌区无重复；2/3/8 人合法出场数；秘密选择不泄露；事件分与逐场总分一致；本场结束后事件资源清理；复杂移动/重掷先完成后再执行其后继效果。

这份资料已经补齐“完整事件表缺失”的问题，但没有补齐全部可执行裁定。开放范围和任何网页专用解释应在产品说明中与作者原文分开标明。
